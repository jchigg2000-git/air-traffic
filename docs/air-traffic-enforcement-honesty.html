01 · The temptation

Every dashboard wants to show you green.

The easiest control plane to build is the one that lies a little. You push a config into a developer's environment, you get a 200 back, and you paint the row ENFORCED. It demos beautifully. It is also how a security team learns — three months and one incident later — that the “enforced” MCP allow‑list was a suggestion a developer turned off on an unmanaged laptop. The setting was real. The claim was a lie.

Air‑Traffic treats that gap as the product. A control isn't “on” or “off” — it has a disposition (how it's actually wired) and, when it's managed config, an enforcement tier (how far that wiring really reaches). The UI is allowed to make exactly the claims the tier can back. No more.

02 · The truthfulness layer

Five dispositions. One is a confession.

Before enforcement even enters the picture, every capability declares how it is controlled. This is a first‑class visual token in the real UI (web/src/lib/dispositions.ts) — a colored chip with a glyph, sourced straight from vendor docs or marked unverified when it isn't.

The honesty starts here: proxy_enforced behaves as monitor‑only until the optional gateway is enabled (off by default), and unverified exists so the system can say “I don't actually know” out loud instead of guessing green.

03 · The enforcement ladder

Of the managed controls, three tiers — and only two are enforced.

Every env_managed capability carries one of three enforcement tiers. The tier is not a label for the marketing page — it decides, mechanically, which sentence the UI is permitted to print and what the drift read‑back says when reality disagrees.

server_side
TIER A

Non‑bypassable. Enforced server‑side.

The vendor or platform holds the line, not the device. GitHub branch protection with enforce_admins: true, a Copilot MCP registry‑only allowlist, a required code‑review status check. A developer cannot turn it off locally.

read-back source: locked · drift: none

mdm_locked
TIER B

Enforced — but only where the MDM profile reaches.

Claude Code managed‑settings.json via mdm://jamf, VS Code via Intune. On an enrolled device it's locked. On an unenrolled one it quietly never applies — so the UI must footnote the condition, never claim it universally.

off‑MDM read‑back → “device not MDM‑enrolled; managed settings not applied”

seed_only
TIER C

Seeded as a default. Watched, never held.

The config is pushed as a starting point; the developer can override it at will. Air‑Traffic detects and reports the override as drift — but it does not block it. This tier is never rendered as “enforced.”

override read‑back → “developer overrode seed‑only config on an unmanaged device”

05 · Under the needle

The refusal is four lines of real code.

There's no AI judgment call in the “don't lie” moment. It's a lookup table and a boolean. The gauge you just dragged runs the exact same logic the production SPA does — the climax is just enforced: false doing its job.

web/src/lib/dispositions.ts
const ENFORCEMENT_LABEL = {
  server_side: { label: 'Server-side', enforced: true  },
  mdm_locked:  { label: 'MDM-locked', enforced: true  },
  seed_only:   { label: 'Seed-only',  enforced: false }, // NEVER shown as "enforced"
}
internal/envconfig/envconfig.go · ReadState
switch artifact.Enforcement {
case EnforcementSeedOnly:
  st.Source = "default"
  if overridden {
    st.Source = "user_override"
    st.DriftDetected = true
    st.DriftMessage = "developer overrode
       seed-only config..."
  }
case EnforcementMDMLocked:
  if overridden { /* not MDM-enrolled */ }
}

The component (DispositionChip.tsx) reads that boolean and nothing else: an enforced tier gets a neutral badge; seed_only gets an amber one titled “Seed‑only — drift‑detected, NOT enforced.” A naive feature can't accidentally print “enforced” — there is no code path that maps Tier C to it.

06 · The normalized signal

Honesty rides the wire, not just the screen.

The same disposition travels off the page. Every normalized audit event carries a control_surface disposition; every divergence becomes a DriftRecord at /api/drift; all of it folds into one ops‑observation‑batch/v1 batch the emitter ships every few seconds — the contract reused verbatim across the fleet.

A SIEM that consumes the audit stream (?format=siem) inherits the same restraint: the word “enforced” never appears next to a Tier‑C control, anywhere downstream.

07 · What this does NOT claim

A page about honesty had better keep its own.

Honest caveats

  • This is the synthetic phase. Phase 1 is a byte‑identical synthetic replica of each vendor's admin surface. The enforcement tiers and drift read‑backs are modeled from that synthetic env‑state, not yet read from live Jamf / Intune / GitHub. The gauge's claim table is the real logic; the device state is illustrative.
  • Only one shipped capability is seed_only today. cron_controls (“Scheduled‑Job Controls”). The tier is first‑class in the model and fully wired; coverage is deliberately small and labeled, not inflated.
  • Tier‑B “enforced” is conditional, not absolute. mdm_locked only holds on enrolled devices; off‑MDM it drifts. We render it enforced with the condition, never as a flat guarantee.
  • proxy_enforced is monitor‑only until you turn the gateway on. The gateway is optional and off unless you start it — so absent one, that disposition behaves as monitoring, and the UI says so. (Written for Phase 1. The inference gateway shipped in Phase 3 on 2026‑07‑02 and now runs as a container in the default stack; see README.md.)
  • This is a rendering rule, not a vendor guarantee. We assert only what we can source; anything we can't confirm from live docs is unverified, not assumed.
